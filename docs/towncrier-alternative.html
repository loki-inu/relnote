A towncrier alternative without news fragments

towncrier (PyPI package towncrier, 26.9.0 docs) builds a news file from news fragments. The 26.9.0 docs say it reads those fragments rather than Git history, so that people do not all write into one file. They name Twisted, pytest, pip, BuildBot, and attrs among the projects that use it. The command line tool requires Python. The same page says it is usable with any project type, as long as you do not use Python-specific affordances such as auto-detection of the project version. If the commits already follow conventional commits and you do not want a fragment file per change, relnote builds the Release body from the local git log: no newsfragments directory, no towncrier.toml, and no [tool.towncrier] table.

Keep towncrier when you want that curated fragment: the 26.9.0 homepage calls it news written for the people who hear it, separate from the developer log. Keep it when towncrier check should require a fragment on each branch, and when you want the Python integration those docs describe (version from package metadata or __version__, fragments in the package's newsfragments directory, [tool.towncrier] in pyproject.toml). Custom fragment types, sections, and templates are part of that config. The homepage also says towncrier works best where merges close an issue.

relnote fits when you do not want a fragment file per change and the commits are already conventional, including a squash-merged title such as feat: … (#12). That includes a repository that is not a Python package: towncrier can run there too, with name set and --version passed when the version cannot be detected, and the reason to switch is the fragment workflow. The CI form is one step, loki-inu/relnote@v0.3.8 after actions/checkout with fetch-depth: 0, or python3 -m relnote --output notes.md --quiet wherever Python 3.11+ and git are already installed. It is a poor fit when the note you want is a sentence that never appears in the commit subject: relnote never sees those fragment files.

Release body, next version, CHANGELOG section

Three separate invocations, the same flags as the offline guide, the next version guide, and the CHANGELOG.md guide. Nothing is pushed, and no fragment file is read. --since REF starts somewhere other than the latest tag.

python3 -m relnote --next-version
python3 -m relnote --output notes.md --quiet
python3 -m relnote --changelog CHANGELOG.md --changelog-title v1.4.0 --quiet

--next-version prints one line, such as v1.4.0. --output notes.md --quiet writes the Release body and prints nothing. --changelog prepends one Markdown section. With --changelog-title v1.4.0 on an untagged HEAD, that section's compare link ends at v1.4.0 (v0.3.6+). Without --changelog-title, an untagged HEAD is titled Unreleased. The command does not commit the file, and it does not take --version as a towncrier version override: the section title is --changelog-title, and the suggested tag is --next-version.

What those commands write

Start: the last tag is v1.3.2, then feat: add --json output (#12) and fix: handle empty config (#13). --next-version prints v1.4.0 (a feat is a minor bump). notes.md is the Release body. Because HEAD is not tagged yet, the range ends at HEAD:

## What's changed

### Features

- add --json output (#12) (`4a5b395`) — Ada Lovelace

### Fixes

- handle empty config (#13) (`7e08d2c`) — Ada Lovelace

Range: `v1.3.2` → `HEAD`.

CHANGELOG.md gains this section above the previous entries. (#12) becomes a pull request link when origin is a github.com remote (v0.3.5+):

Both blocks come from running those three commands against a scratch repository in relnote's test suite (tests/test_towncrier_docs.py). Your hashes and the date differ. A squash-merged pull request whose title is already feat: … (#12) is one commit, so it shows up as one line. towncrier would list a fragment such as 12.feature instead, under that fragment type. Migration

  1. Install the zipapp above and pin it to v0.3.8. Stop running towncrier build and towncrier check in CI and locally.
  2. If fragment files for this release are still in the tree, run towncrier once so the tutorial's production step folds them into the news file, or copy the sentences you still want. relnote does not read those files.
  3. Leave the existing news file in the repo. relnote's --changelog writes a Markdown section (## [TITLE] - DATE) and does not look for .. towncrier release notes start or the Markdown comment. If the towncrier file is NEWS.rst, keep it as history and point --changelog at a CHANGELOG.md. If it is already Markdown with ## headings, the next run inserts one section before the first of those headings. Older text stays. The command does not git rm fragments and does not commit.
  4. Remove the towncrier dependency when nothing else imports it. towncrier.toml and [tool.towncrier] are unused after that. Delete the fragments directory once it no longer holds notes you need.
  5. Publish the GitHub Release with the workflows on the Action guide, copied below. relnote still does not push.

A Python package that also wants the version in pyproject.toml bumped, the changelog section committed, and an annotated tag can use examples/release.sh. --dry-run prints the plan and writes nothing. Nothing in the script is pushed. Guide: Python package releases.

curl -fsSL -o release.sh https://raw.githubusercontent.com/loki-inu/relnote/v0.3.8/examples/release.sh
chmod +x release.sh
./release.sh --dry-run --bump-file pyproject.toml
./release.sh --bump-file pyproject.toml

That URL is examples/release.sh on the v0.3.8 tag. The v0.3.8 release assets are relnote, relnote.pyz, and SHA256SUMS, so the script is not a release asset. It calls relnote on PATH.

Draft a Release when the tag is pushed

This is the tag-push workflow from the GitHub Action guide and from examples/draft-release.yml. Copy it to .github/workflows/draft-release.yml. Push a tag such as v1.4.0 and a draft Release appears with the notes since the previous tag. You review it and press Publish. There is no towncrier build step and no news fragment to collect.

name: Draft release

on:
  push:
    tags:
      - "v*"

jobs:
  draft:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: relnote
        uses: loki-inu/relnote@v0.3.8
      - uses: softprops/action-gh-release@v2
        with:
          draft: true
          name: ${{ github.ref_name }}
          body: ${{ steps.relnote.outputs.notes }}

fetch-depth: 0 is required so the checkout has tags. contents: write is for the release step. The relnote step only reads the checkout. On a tag push, HEAD is the new tag, so the range and the compare link end at that tag (v0.3.4+), not at HEAD.

No third-party release action? The guide's GitHub CLI step passes the notes through the environment, not inline in the script (commit subjects contain backticks):

      - run: gh release create "$GITHUB_REF_NAME" --draft --title "$GITHUB_REF_NAME" --notes "$NOTES"
        env:
          GH_TOKEN: ${{ github.token }}
          NOTES: ${{ steps.relnote.outputs.notes }}

Or create the Release from a button

This is the workflow_dispatch job from the same guide. next-version is the tag. has-changes is false when there is nothing new, and the step still succeeds, so the gh step is gated on it. gh release create makes the tag at --target.

name: Release
on:
  workflow_dispatch:
permissions:
  contents: write
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: relnote
        uses: loki-inu/relnote@v0.3.8
      - if: steps.relnote.outputs.has-changes == 'true'
        run: gh release create "$TAG" --target "$GITHUB_SHA" --title "$TAG" --notes "$NOTES"
        env:
          GH_TOKEN: ${{ github.token }}
          TAG: ${{ steps.relnote.outputs.next-version }}
          NOTES: ${{ steps.relnote.outputs.notes }}
      - if: steps.relnote.outputs.has-changes != 'true'
        run: echo "Nothing to release since the last tag."

Set fail-on-empty: true if an empty range should fail the step. An unknown since ref still fails. Inputs and outputs: the Action guide.

FAQ

When should I keep towncrier?

Keep towncrier when you want a curated news fragment per change, written for people who use the software, when you want towncrier check to require a fragment on a branch, or when you want the Python package integration in the 26.9.0 docs: version from package metadata or __version__, fragments in the package newsfragments directory, and config in pyproject.toml. relnote does not read fragment files and does not check that a branch added one.

Does relnote read news fragments?

No. relnote reads commit subjects since the previous tag (or --since). towncrier 26.9.0 reads fragment files such as 1234.bugfix and, by default, removes the processed fragments on build. A fragment file is not an input to relnote.

Does relnote read towncrier.toml or pyproject.toml?

No. towncrier 26.9.0 reads towncrier.toml or pyproject.toml under [tool.towncrier]. If both exist, towncrier.toml takes precedence. relnote has no config file and does not read either one. --changelog-title names the section you pass. --next-version prints the next tag from the commits. towncrier does not compute that tag; it uses --version, the version key, or, for a Python package, package metadata or __version__.

How is this different from the Changesets page?

The Changesets page is for .changeset markdown files in a JavaScript monorepo, with per-package tags. This page is for towncrier news fragments, often one news file for a Python project. The github-changelog-generator page rebuilds CHANGELOG.md from the GitHub API. relnote, on all three, reads the local git log instead of those extra files or API calls.

Should I pin versions?

Yes. Pin the curl URL and the loki-inu/relnote action to the same tag (this page uses v0.3.8). The towncrier facts here are from the Towncrier 26.9.0 documentation (tutorial, command line reference, and configuration reference), not from an unreleased change. Floating latest on the relnote zipapp can change behaviour under you.

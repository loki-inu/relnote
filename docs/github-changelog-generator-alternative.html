A github-changelog-generator alternative without a GitHub token

github-changelog-generator (Ruby gem github_changelog_generator, repository github-changelog-generator/github-changelog-generator) rebuilds a changelog from GitHub tags, closed issues, and merged pull requests. The published gem is 1.18.0. If the commits already follow conventional commits and you want a GitHub Release body plus one new CHANGELOG.md section, relnote does that from the local git log: no Ruby gem, no config file, and no token to generate the notes.

Keep github-changelog-generator when the changelog should list closed issues and merged pull requests grouped by labels, when those issues are not already conventional commit subjects, when CHANGELOG.md should be rebuilt from GitHub tags, or when the repository is on GitHub Enterprise (--github-site and --github-api). The README's Rake task is the path to keep if generation should stay a rake target in a Ruby project.

relnote is the better fit when commits are already conventional, including squash-merged titles such as feat: … (#12), and you want those subjects grouped with no label list and no API call. It is also the fit when older changelog entries must stay untouched, when the release tooling should not be a Ruby gem, and when the next step is a GitHub Release body. It is a poor fit when the history you care about is GitHub issues that never became commit subjects: relnote never sees those issues.

Install

What you are leaving, from the 1.18.0 README:

gem install github_changelog_generator
github_changelog_generator -u USER -p PROJECT

The same README says you may need sudo gem install github_changelog_generator on Linux. A Gemfile development group is the other install it documents: gem 'github_changelog_generator', require: false.

Python 3.11+ and git on PATH. The download is the v0.3.7 zipapp from the GitHub Release, the same pin as the single-file install. From a checkout, python3 -m relnote is the same CLI. pip install git+https://github.com/loki-inu/relnote.git is the other install on the offline release notes page. Remove github_changelog_generator from the Gemfile when nothing else loads it. relnote does not read .github_changelog_generator.

mkdir -p ~/.local/bin

chmod +x ~/.local/bin/relnote

Release body, next version, CHANGELOG section

Three separate invocations, the same flags as the offline guide, the next version guide, and the CHANGELOG.md guide. Nothing is pushed, and no GitHub API is called. --since REF starts somewhere other than the latest tag, which is the relnote equivalent of --since-tag for a single git range.

python3 -m relnote --next-version
python3 -m relnote --output notes.md --quiet
python3 -m relnote --changelog CHANGELOG.md --changelog-title v1.4.0 --quiet

--next-version prints one line, such as v1.4.0. --output notes.md --quiet writes the Release body and prints nothing. --changelog prepends one section. With --changelog-title v1.4.0 on an untagged HEAD, that section's compare link ends at v1.4.0 (v0.3.6+). Without --changelog-title, an untagged HEAD is titled Unreleased. The command does not commit the file, and it does not take --user or --project.

What those commands write

Start: the last tag is v1.3.2, then feat: add --json output (#12) and fix: handle empty config (#13). --next-version prints v1.4.0 (a feat is a minor bump). notes.md is the Release body. Because HEAD is not tagged yet, the range ends at HEAD:

## What's changed

### Features

- add --json output (#12) (`4a5b395`) — Ada Lovelace

### Fixes

- handle empty config (#13) (`7e08d2c`) — Ada Lovelace

---

Range: `v1.3.2` → `HEAD`.

**Full changelog:** https://github.com/you/project/compare/v1.3.2...HEAD

CHANGELOG.md gains this section above the previous entries. (#12) becomes a pull request link when origin is a github.com remote (v0.3.5+):

## [v1.4.0] - 2026-11-19

### Features

- add --json output ([#12](https://github.com/you/project/pull/12)) (`4a5b395`) — Ada Lovelace

### Fixes

- handle empty config ([#13](https://github.com/you/project/pull/13)) (`7e08d2c`) — Ada Lovelace

**Full changelog:** https://github.com/you/project/compare/v1.3.2...v1.4.0

Both blocks come from running those three commands against a scratch repository in relnote's test suite (tests/test_github_changelog_generator_docs.py). Your hashes and the date differ. A squash-merged pull request whose title is already feat: … (#12) is one commit, so it shows up as one line. The gem would list that pull request from the GitHub API instead, under the label section that matches. Details: squash-merged PR titles.

Migration

  1. Install the zipapp above and pin it to v0.3.7. Stop running github_changelog_generator in CI and locally. You can drop CHANGELOG_GITHUB_TOKEN from the job that only generated the changelog.
  2. Leave the current CHANGELOG.md in the repo. The next --changelog run inserts one section before the first ## heading. Older sections are not rewritten. relnote does not read HISTORY.md and does not append --base. If the gem already folded HISTORY.md into CHANGELOG.md, that text stays where it is.
  3. Remove the gem. The 1.18.0 README's Gemfile example is gem 'github_changelog_generator', require: false inside a :development group. Delete a GitHubChangelogGenerator::RakeTask from the Rakefile if that task only existed to refresh the changelog. .github_changelog_generator is unused after that. Delete it once nothing else reads it.
  4. Publish the GitHub Release with the workflows on the Action guide, copied below. relnote still does not push. The gem's own release example (gh release create with --notes-file) is a separate step you no longer need for the notes file it wrote.

examples/release.sh is the local stand-in for choosing the version, prepending the section, committing, and tagging. --dry-run prints the plan and writes nothing. --bump-file package.json sets the first version line. Nothing in the script is pushed. The gem's --future-release only names the unreleased section. It does not edit a version file.

curl -fsSL -o release.sh https://raw.githubusercontent.com/loki-inu/relnote/v0.3.7/examples/release.sh
chmod +x release.sh
./release.sh --dry-run --bump-file package.json
./release.sh --bump-file package.json

That URL is examples/release.sh on the v0.3.7 tag. The v0.3.7 release assets are relnote, relnote.pyz, and SHA256SUMS, so the script is not a release asset. It calls relnote on PATH.

Monorepos: the gem takes one --user and one --project, which is one GitHub repository. relnote does not split a GitHub repository into packages by itself. Pass --path and --tag-prefix (or release.sh --tag-prefix) so notes and --next-version only see one package. Guide: monorepo release notes.

Draft a Release when the tag is pushed

This is the tag-push workflow from the GitHub Action guide and from examples/draft-release.yml. Copy it to .github/workflows/draft-release.yml. Push a tag such as v1.4.0 and a draft Release appears with the notes since the previous tag. You review it and press Publish. There is no github_changelog_generator step and no Ruby install.

name: Draft release

on:
  push:
    tags:
      - "v*"

jobs:
  draft:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: relnote
        uses: loki-inu/relnote@v0.3.7
      - uses: softprops/action-gh-release@v2
        with:
          draft: true
          name: ${{ github.ref_name }}
          body: ${{ steps.relnote.outputs.notes }}

fetch-depth: 0 is required so the checkout has tags. contents: write is for the release step. The relnote step only reads the checkout. On a tag push, HEAD is the new tag, so the range and the compare link end at that tag (v0.3.4+), not at HEAD.

No third-party release action? The guide's GitHub CLI step passes the notes through the environment, not inline in the script (commit subjects contain backticks):

      - run: gh release create "$GITHUB_REF_NAME" --draft --title "$GITHUB_REF_NAME" --notes "$NOTES"
        env:
          GH_TOKEN: ${{ github.token }}
          NOTES: ${{ steps.relnote.outputs.notes }}

Or create the Release from a button

This is the workflow_dispatch job from the same guide. next-version is the tag. has-changes is false when there is nothing new, and the step still succeeds, so the gh step is gated on it. gh release create makes the tag at --target.

name: Release
on:
  workflow_dispatch:
permissions:
  contents: write
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: relnote
        uses: loki-inu/relnote@v0.3.7
      - if: steps.relnote.outputs.has-changes == 'true'
        run: gh release create "$TAG" --target "$GITHUB_SHA" --title "$TAG" --notes "$NOTES"
        env:
          GH_TOKEN: ${{ github.token }}
          TAG: ${{ steps.relnote.outputs.next-version }}
          NOTES: ${{ steps.relnote.outputs.notes }}
      - if: steps.relnote.outputs.has-changes != 'true'
        run: echo "Nothing to release since the last tag."

Set fail-on-empty: true if an empty range should fail the step. An unknown since ref still fails. Inputs and outputs: the Action guide.

FAQ

When should I keep github-changelog-generator?

Keep it when CHANGELOG.md should be rebuilt from GitHub tags, closed issues, and merged pull requests grouped by labels, when those issues are not conventional commit subjects, or when the repository is on GitHub Enterprise (--github-site and --github-api). relnote reads the local git log, prepends one section, and does not call the GitHub API to generate notes.

Does relnote need a token to generate notes?

No. The CLI and the loki-inu/relnote action read the local checkout only. github_changelog_generator 1.18.0 fetches tags, closed issues, and merged pull requests through the GitHub API. Its --token help says a GitHub token is required to make more than 50 requests per hour. Pass --token or set CHANGELOG_GITHUB_TOKEN. The README says a private repository needs that token with the repo scope. The later step that creates the Release uses github.token, as on the GitHub Action guide.

Does relnote rebuild CHANGELOG.md from every tag?

No. github_changelog_generator overwrites the output file (default CHANGELOG.md) with entries for the tags it includes, then appends HISTORY.md when that file exists (the default of --base). relnote inserts one section before the first ## heading and leaves older sections as they were. A duplicate title is refused. The command does not commit.

How is this different from the Release Drafter and auto-changelog pages?

The Release Drafter page is for a GitHub Action that updates a draft Release from pull request labels. The auto-changelog page is for the npm package that rebuilds CHANGELOG.md from local semver tags. This page is for the Ruby gem github_changelog_generator, which rebuilds CHANGELOG.md from GitHub issues and pull requests and needs a token because of the API rate limit.

Should I pin versions?

Yes. Pin the curl URL and the loki-inu/relnote action to the same tag (this page uses v0.3.7). The github-changelog-generator facts here are from the published 1.18.0 README, gemspec, and parser, not from an unreleased change. Floating latest on the relnote zipapp can change behaviour under you.

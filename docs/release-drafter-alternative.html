A Release Drafter alternative without PR labels

Release Drafter (release-drafter/release-drafter) drafts the next GitHub Release as pull requests merge. Its example workflow runs on push to the default branch, and .github/release-drafter.yml groups those pull requests by labels. If the commits already follow conventional commits, relnote builds the Release body from the local git log: no labels to maintain, no config file, and no token to generate the notes.

Install

Python 3.11+ and git on PATH. The download is the v0.3.7 zipapp from the GitHub Release, the same pin as the single-file install. From a checkout, python3 -m relnote is the same CLI. pip install git+https://github.com/loki-inu/relnote.git is the other install on the offline release notes page.

mkdir -p ~/.local/bin
curl -fsSL -o ~/.local/bin/relnote https://github.com/loki-inu/relnote/releases/download/v0.3.7/relnote
chmod +x ~/.local/bin/relnote

Release body, next version, CHANGELOG section

Three separate invocations, the same flags as the offline guide, the next version guide, and the CHANGELOG.md guide. Nothing is pushed, and no GitHub API is called. --since REF starts somewhere other than the latest tag.

python3 -m relnote --next-version
python3 -m relnote --output notes.md --quiet
python3 -m relnote --changelog CHANGELOG.md --changelog-title v1.4.0 --quiet

--next-version prints one line, such as v1.4.0. --output notes.md --quiet writes the Release body and prints nothing; paste notes.md into a new or existing Release. --changelog prepends one section. With --changelog-title v1.4.0 on an untagged HEAD, that section's compare link ends at v1.4.0 (v0.3.6+). The command does not commit the file.

What those commands write

Start: the last tag is v1.3.2, then feat: add --json output (#12) and fix: handle empty config (#13). --next-version prints v1.4.0. notes.md is the Release body. Because HEAD is not tagged yet, the range ends at HEAD:

## What's changed

### Features

- add --json output (#12) (`4a5b395`) — Ada Lovelace

### Fixes

- handle empty config (#13) (`7e08d2c`) — Ada Lovelace

---

Range: `v1.3.2` → `HEAD`.

**Full changelog:** https://github.com/you/project/compare/v1.3.2...HEAD

CHANGELOG.md gains this section above the previous entries. (#12) becomes a pull request link when origin is a github.com remote (v0.3.5+):

## [v1.4.0] - 2026-11-17

### Features

- add --json output ([#12](https://github.com/you/project/pull/12)) (`4a5b395`) — Ada Lovelace

### Fixes

- handle empty config ([#13](https://github.com/you/project/pull/13)) (`7e08d2c`) — Ada Lovelace

Both blocks come from running those three commands against a scratch repository in relnote's test suite (tests/test_release_drafter_docs.py). Your hashes and the date differ. A squash-merged pull request whose title is already feat: … (#12) is one commit, so it shows up as one line. Merge commits are omitted. Details: squash-merged PR titles.

Draft a Release when the tag is pushed

This is the tag-push workflow from the GitHub Action guide and from examples/draft-release.yml. Copy it to .github/workflows/draft-release.yml. Push a tag such as v1.4.0 and a draft Release appears with the notes since the previous tag. You review it and press Publish. It does not refresh a draft on every merge to the default branch.

name: Draft release

on:
  push:
    tags:
      - "v*"

jobs:
  draft:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: relnote
        uses: loki-inu/relnote@v0.3.7
      - uses: softprops/action-gh-release@v2
        with:
          draft: true
          name: ${{ github.ref_name }}
          body: ${{ steps.relnote.outputs.notes }}

fetch-depth: 0 is required so the checkout has tags. contents: write is for the release step. The relnote step only reads the checkout. On a tag push, HEAD is the new tag, so the range and the compare link end at that tag (v0.3.4+), not at HEAD.

No third-party release action? The guide's GitHub CLI step passes the notes through the environment, not inline in the script (commit subjects contain backticks):

      - run: gh release create "$GITHUB_REF_NAME" --draft --title "$GITHUB_REF_NAME" --notes "$NOTES"
        env:
          GH_TOKEN: ${{ github.token }}
          NOTES: ${{ steps.relnote.outputs.notes }}

Or create the Release from a button

This is the workflow_dispatch job from the same guide. next-version is the tag. has-changes is false when there is nothing new, and the step still succeeds, so the gh step is gated on it. gh release create makes the tag at --target.

name: Release
on:
  workflow_dispatch:
permissions:
  contents: write
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: relnote
        uses: loki-inu/relnote@v0.3.7
      - if: steps.relnote.outputs.has-changes == 'true'
        run: gh release create "$TAG" --target "$GITHUB_SHA" --title "$TAG" --notes "$NOTES"
        env:
          GH_TOKEN: ${{ github.token }}
          TAG: ${{ steps.relnote.outputs.next-version }}
          NOTES: ${{ steps.relnote.outputs.notes }}
      - if: steps.relnote.outputs.has-changes != 'true'
        run: echo "Nothing to release since the last tag."

Set fail-on-empty: true if an empty range should fail the step. An unknown since ref still fails. Inputs and outputs: the Action guide.

Map the example categories to commit types

The labels below are the ones in Release Drafter's documented .github/release-drafter.yml example. relnote has no label list; the commit type is the category.

Release Drafter examplerelnote
feature, enhancement (Features, semver-increment: minor)feat: or feat(scope): → Features. --next-version bumps minor
fix, bugfix, bug (Bug Fixes; increment defaults to patch)fix: → Fixes. --next-version bumps patch
chore (Maintenance)chore, docs, refactor, and any other type, including a subject that is not a conventional commit → Other. Patch, unless the range also has a feat or a breaking change
major label (type: version-resolver, semver-increment: major)type! (for example feat!:) or a BREAKING CHANGE: footer → Breaking. Major bump, or minor while the version is 0.y.z
skip-changelog (type: pre-exclude)No label. Merge commits are omitted. chore(release): … is omitted unless you pass --include-release-commits (action input include-release-commits: true)
when.conventional.type: feat on the pull request titleAlready how feat commits are grouped. No config key. A squash merge keeps the title as the commit subject

Release Drafter's version resolver picks the highest matching semver-increment. relnote does the same kind of choice from the commit categories in the range, with the 0.y.z exception above. A version-resolver category with no when is Release Drafter's fallback; the example sets that fallback to patch. relnote's fallback is also patch, when the range has no breaking change and no feat.

FAQ

When should I keep Release Drafter?

Keep it when pull requests are labeled and commits are not conventional, when you want one draft release updated on every push to the default branch, or when you want Autolabeler to apply labels from the title, branch, files, or body. relnote does not read labels and does not update a draft on each merge.

Does relnote need a token to generate notes?

No. The CLI and the loki-inu/relnote action read the local checkout only. They are not a GitHub App. The later step that creates the Release uses github.token, as on the GitHub Action guide. Release Drafter's example needs contents: write and pull-requests: read because it reads pull requests and writes the draft through the GitHub API.

Does this update a draft on every merge?

No. Release Drafter's example workflow runs on push to the default branch and creates or updates one draft. The workflows on this page create a Release when you push a tag, or when you run the workflow_dispatch job. They do not edit a draft each time a pull request merges.

How is this different from the git-cliff and release-please pages?

The git-cliff alternative replaces a Rust changelog binary and cliff.toml. The release-please alternative replaces a release pull request, including the version bump and tag via examples/release.sh. This page replaces label-based draft notes. The publish steps are the ones already on the Action guide.

Should I pin versions?

Yes. Pin the curl URL and the loki-inu/relnote action to the same tag (this page uses v0.3.7). Floating latest can change behaviour under you.
